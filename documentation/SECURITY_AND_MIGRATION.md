# Secure Vault and legacy migration

Last reviewed: **2026-08-23**.

Muse Secure Vault separates authentication from decryption:

- **Email/password and passkeys authenticate an account or device.** A passkey
  is a WebAuthn credential. Muse stores only its credential ID, public key,
  counter, transport/device metadata, timestamps, and revocation state. Its
  private key stays in the platform authenticator or security key.
- **The AES recovery key decrypts content.** It is a 32-byte Base64URL value
  generated by the browser or supplied by the user. The browser imports it as
  a non-extractable AES-GCM `CryptoKey` in IndexedDB. It is never put in
  Supabase Vault, Postgres, browser logs, analytics, or email.
- **The Ollama API key is separate.** It remains in Supabase Vault so the
  server can make an explicitly authorized Ollama request without returning
  the API key to the browser.

## User lifecycle

1. A user signs up or signs in with email/password for compatibility.
2. The Secure Vault setup screen saves the required Ollama API key in the
   server-side Vault, generates or accepts the recovery key, and requires
   download/copy and last-six-character confirmation. The user may optionally
   create a passkey there, or add one later in Devices & Security.
3. Muse shows this warning: **“Save this recovery key somewhere safe. You need
   it to decrypt your Muse vault on a new device. Muse cannot recover it for
   you.”**
4. On another device, the user signs in with email/password or a synced
   passkey, enters the same recovery key, and Muse verifies it by decrypting
   the per-user vault-check envelope. The user can then optionally add a new
   passkey for that device. Adding or revoking a passkey never rotates or
   replaces the AES key.

If the recovery key is lost, new-device decryption is impossible by design.
An already unlocked device can continue to read its locally stored
non-extractable key, but Muse cannot reconstruct or reset the shared key
without making existing ciphertext inaccessible.

## Encryption model

Each new secure record is encrypted in the browser with AES-256-GCM:

- 96-bit randomly generated nonce per write;
- envelope form `v2.<base64url nonce>.<base64url ciphertext>`;
- additional authenticated data: `<user-id>:<record-id>:v2`;
- opaque server fields only: record ID, owner, record type, revision, lifecycle
  timestamps, and ciphertext.

Note title/content, tags, tasks, summary, specialized fields, report metadata,
research artifacts, and attachment payloads are inside encrypted envelopes.
The client derives filtering and tag-only graph edges after unlock. Migrated
and new images are stored as encrypted attachment records; secure note image
data is kept offline-capable inside the encrypted note envelope.

The server-side `DATA_ENCRYPTION_KEY` remains necessary only to read retained
legacy rows during migration. Do not remove, rotate, or lose it until legacy
retention has ended and backups have been validated.

## Passkey and session controls

`@simplewebauthn/browser` and `@simplewebauthn/server` implement registration
and assertion verification. Registration/authentication challenges are SHA-256
hashed at rest, expire after five minutes, and are marked used after successful
verification. Assertion counters must advance when the authenticator supports
them; a backward counter is rejected as a potential cloned credential.

A verified passkey receives a Secure, HttpOnly Muse session cookie. Passkeys
are optional: password sign-in creates the same short-lived app session for
fallback and migration. Devices & Security lists passkeys and last-used time,
supports adding credentials, and lets a user revoke a credential. Neither
method decrypts vault contents without the recovery key.

Production requirements:

```dotenv
PUBLIC_URL=https://notes.example.com
WEBAUTHN_RP_ID=notes.example.com
WEBAUTHN_RP_NAME=Muse
WEBAUTHN_ORIGINS=https://notes.example.com
MUSE_SESSION_SECRET=<at-least-32-random-characters>
VAULT_LEGACY_MIGRATION=enabled
```

`MUSE_SESSION_SECRET` and `VAULT_LEGACY_MIGRATION` are used for all Secure
Vault accounts. `WEBAUTHN_*` values are needed only when offering passkeys.
Use HTTPS for WebAuthn in production. The RP ID must be a hostname—not a
URL—and must match the browser origin’s RP-ID rules. Set all allowed origins
explicitly; do not use `*` with credentialed CORS. Rotate
`MUSE_SESSION_SECRET` only with a planned sign-out of existing app sessions.

## Additive migration and rollback

The migration is intentionally additive. Apply
`supabase/migrations/008_secure_vault.sql` before deploying the corresponding
server/client build:

```bash
docker compose exec -T db sh -ec 'PGPASSWORD="$POSTGRES_PASSWORD" psql -U supabase_admin -d postgres' < supabase/migrations/008_secure_vault.sql
docker compose up -d --build server nginx
```

Before inviting users to migrate:

1. Back up Postgres and the persistent `docker/pgsodium_root.key`.
2. Confirm `DATA_ENCRYPTION_KEY` is the key that decrypts representative
   legacy notes, reports, documents, and artifacts.
3. Keep `VAULT_LEGACY_MIGRATION=enabled`.

After a user completes vault setup, their unlocked browser calls the temporary,
authenticated compatibility export. It copies notes, tasks, tags, research
documents/artifacts, report metadata, and images into `vault_records`, keeping
logical note IDs and lifecycle timestamps. It verifies that every migrated note
decrypts in the same browser before setting `user_vaults.migration_status` to
`verified`. A failed copy sets `failed`; it does not delete or alter the
legacy rows, so the user may retry after resolving the cause.

Useful administrator verification queries:

```sql
select migration_status, count(*) from public.user_vaults group by migration_status;
select user_id, record_type, count(*) from public.vault_records group by user_id, record_type order by user_id, record_type;
select n.user_id, count(*) as legacy_notes, count(v.id) filter (where v.record_type = 'note') as vault_notes
from public.notes n left join public.vault_records v on v.id = n.id
group by n.user_id order by n.user_id;
```

Rollback means serving the previous application build while keeping migration
008 and all legacy rows. It is safe because the migration neither overwrites
nor deletes legacy data. Do **not** auto-purge `notes`, `tasks`, tags,
documents, artifacts, reports, images, `ai_jobs`, or Qdrant vectors.

Only after every required account is verified, backups have been restored into
a non-production environment, and an administrator has signed off may you set
`VAULT_LEGACY_MIGRATION=disabled` and run a separately reviewed purge plan.
That destructive purge is deliberately not shipped as an automatic migration.

## AI disclosure and privacy

For an encrypted note, selecting AI assist immediately starts a foreground SSE
request and displays “Muse is thinking.” Before the first request in a browser
session, Muse explains that selected decrypted text goes to Ollama using the
user’s stored API key. The server does not write decrypted prompts or results
to `ai_jobs`, reports, logs, or Qdrant; it returns the proposed patch over the
open response. Closing the tab/vault cancels the active request. Specialized
notes require an explicit apply/discard decision after an AI proposal.

Cross-note RAG and persisted background web-research jobs remain unavailable
inside an encrypted vault because they would require durable decrypted context.
Legacy accounts retain their existing queue and research behavior until they
migrate. This boundary is intentional, not a decryption failure.
